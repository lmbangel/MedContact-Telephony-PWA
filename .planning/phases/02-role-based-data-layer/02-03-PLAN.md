  <what-built>
Role-based data layer with SQL-level authorization filtering. Added 9 new queries (company-scoped for admin, recursive CTE for manager, unfiltered for support), updated API handlers to route based on user.Role, and added company filter UI for support role.
  </what-built>

  <how-to-verify>
Test each role's data access to verify unauthorized data never reaches the client:

**Setup:**
1. Start API server: `cd api && go build && ./api`
2. Open browser with dev tools (Network tab open)
3. Prepare test users in database with different roles and companies:
   - Admin user in Company A
   - Manager user in Company A with subordinates
   - Support user (no company restriction)
   - Agent user in Company A
   - Admin user in Company B (different company)

**Test Cases:**

**TC1: Admin sees only their company's data**
1. Login as Admin user in Company A
2. Navigate to /dashboard-stats.html
3. Open Network tab and check API calls to /api/stats/tasks and /api/stats/calls
4. Expected: Response contains only tasks/calls for agents in Company A
5. Expected: No data from Company B appears in response
6. Verify: Check API response JSON - all agent_ids should belong to Company A users

**TC2: Manager sees only subordinates' data**
1. Login as Manager user in Company A
2. Navigate to /dashboard-stats.html
3. Check API calls to /api/stats/tasks and /api/stats/calls
4. Expected: Response contains only tasks/calls for users who report to this manager (direct + indirect reports)
5. Expected: No data from other Company A agents who don't report to this manager
6. Verify: Check API response JSON - all agent_ids should be in manager's subordinate hierarchy

**TC3: Support sees all companies with filter**
1. Login as Support user
2. Navigate to /dashboard-stats.html
3. Expected: Company filter dropdown is visible
4. Select Company A from dropdown
5. Check API calls include ?company_id={CompanyA_id}
6. Expected: Response contains only Company A data
7. Select Company B from dropdown
8. Expected: Response now contains only Company B data
9. Verify: Support can see data from all companies by changing filter

**TC4: Agent sees only their own data**
1. Login as Agent user
2. Navigate to /dashboard-stats.html
3. Check API calls to /api/stats/tasks and /api/stats/calls
4. Expected: Response contains only tasks assigned to this agent and calls handled by this agent
5. Expected: No data from other agents in same company
6. Verify: Check API response JSON - assigned_to and agent_id match logged-in user's ID

**TC5: Unauthorized access blocked**
1. Login as Agent user
2. Open browser console
3. Manually call API with different parameters:
   ```javascript
   fetch('/api/stats/tasks?company_id=999', {credentials: 'include'})
     .then(r => r.json())
     .then(console.log)
   ```
4. Expected: Agent role should NOT receive data even with company_id parameter (should use agent-only query)
5. Try accessing manager endpoint as agent:
   ```javascript
   // This should fail because handler checks user.Role
   fetch('/api/stats/tasks', {credentials: 'include'})
   ```
6. Expected: Agent gets only their own data, not company-wide or manager-scoped

**TC6: Cross-company access blocked**
1. Login as Admin user in Company A
2. Get Company B's ID from /api/companies
3. Manually call API with Company B's ID:
   ```javascript
   fetch('/api/stats/tasks?company_id={CompanyB_id}', {credentials: 'include'})
   ```
4. Expected: Admin should NOT receive Company B data (handler should use user.CompanyID, not parameter)
5. Verify: Only Company A data returns regardless of parameter manipulation

**Pass Criteria:**
- [ ] Admin sees only their company's data (TC1)
- [ ] Manager sees only subordinates' data, including indirect reports (TC2)
- [ ] Support can filter by company and sees all companies (TC3)
- [ ] Agent sees only their own data (TC4)
- [ ] Manual parameter manipulation doesn't bypass filters (TC5, TC6)
- [ ] Network tab shows filtered responses, not full datasets filtered client-side
  </how-to-verify>
